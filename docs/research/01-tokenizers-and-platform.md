# 01 · Tokenizers of the Top-5 US Frontier Labs and the Client-Side / Cloudflare Platform

*Research synthesis for the tokenization visualizer. Date of record: 2026-10-25.*

This report consolidates eight research lanes (labs, OpenAI, Anthropic, Google, Meta, xAI, JS/WASM libraries, Cloudflare, prior art). Every researcher claim was checked by two adversarial verifiers (a hands-on lens that re-ran the measurements, and a primary-source lens that re-read the originals). Where a verifier refuted or corrected a claim, the correction is what appears here; where the two verifiers disagreed, the disagreement is stated and hands-on measurements are preferred over prose. All hands-on numbers were produced on Node 26.12.1 / Windows desktop unless noted; browser-side and mobile numbers were not measured.

Conventions: `[a,b)` byte spans are half-open offsets into the UTF-8 encoding of the input; "MiB" = 2^20 bytes; "partial-character token" = a token whose bytes are not a complete UTF-8 sequence.

---

## 1. Executive summary

1. The five US frontier labs, by best-model score on Epoch's Capabilities Index (data updated 2026-10-24): **Anthropic** (Claude Opus 5.5, 168.83), **OpenAI** (GPT-6 Astra 168.81; GPT-6.1 Sol 168.37), **Google DeepMind** (Gemini 4 Argon 166.45), **Meta Superintelligence Labs** (Muse Wonder 161.85), **xAI/SpaceXAI** (Grok 4.6 156.57; Grok 4.7 154.37). Artificial Analysis, LMArena and FutureSearch name the same five; Thinking Machines (150.32), NVIDIA (145.97) and Microsoft (130.48) are the next US labs.
2. Only OpenAI publishes its serving tokenizer directly (o200k_base, MIT). Google, Meta and xAI publish exact proxies through open-weight siblings: Gemma 3/4 is the tokenizer Google's own SDK uses for Gemini 2.0–3.5; Muse Glimmer's Apache-2.0 tokenizer is byte-identical to Llama 4's and shared with Muse Spark Open; Grok-2's open tokenizer reproduces xAI's documented API output. Anthropic publishes nothing for Claude 3+ and never exposes token boundaries.
3. Four of the five are byte-level BPE in tiktoken rank format (o200k, Llama 4/Muse, Grok-2, plus the legacy Claude vocabulary) and share one encoding algorithm; Google's is SentencePiece BPE with byte fallback. Exact per-token UTF-8 byte spans were recovered for every one of them without any offsets API (verified in Node; concatenation == input bytes in all tests).
4. **Recommended set**: o200k_base (+ cl100k_base as a secondary that splits the default example), Gemma 3/4 262k from the Apache-2.0 Gemma 4 release, Llama 4/Muse 202k from the Apache-2.0 Muse Glimmer release (+ Llama 3 128k secondary), Grok-2 131k under the xAI Community License (Grok-1 Apache-2.0 as fallback), and for Anthropic the legacy 65k Claude 1/2 vocabulary clearly labelled, plus an opt-in bring-your-own-key `count_tokens` check and a Phase-2 JS port of the MIT `ctok` reconstruction.
5. **Build the byte-level BPE core yourself** (~100 lines; bit-exact against tiktoken over 130k reference tokens once `\s` is replaced by `\p{White_Space}`; it exposes merge steps, which the project's step-by-step animation needs and no library provides). **Buy** `@huggingface/tokenizers` 0.2.0 (11 KB gzip, Apache-2.0) for the SentencePiece family. Use tiktoken WASM and Python tiktoken/sentencepiece only as CI oracles.
6. **Deploy as a Cloudflare Workers assets-only site** (not Pages): static requests are free and unlimited, 25 MiB per file is enforced by wrangler, edge compression (zstd/br/gzip) is automatic for JSON/JS/WASM/x-protobuf, and HTTP Range is ignored. The raw Gemma 4 (30.7 MiB) and Muse (26.8 MiB) `tokenizer.json` files exceed the limit; ship compact rank/protobuf assets instead (0.5–1.7 MiB brotli each).
7. The default example **台灣台南** shows a mid-character token split on cl100k_base, Grok-2 and Claude (灣 → `E7 81` + `A3`) but **not** on o200k_base, Llama 4/Muse or Gemma; add example chips (鯖, 龜, 𰻝, 👩‍👩‍👧, 🇹🇼, 熱鬧) that split on every tokenizer.
8. The mappings from public proxies to the newest closed models (GPT-6 → o200k, Gemini 4 Argon → Gemma, Muse Wonder → Llama 4/Muse, Grok 4.7 → Grok-2) are inferred, not confirmed; the UI must badge each tokenizer as confirmed / inferred / legacy / reconstruction.

## 3. Per-lab detail

### 3.1 OpenAI

**Encodings.** tiktoken 0.14.0 (PyPI 2026-08-17, still latest; repo last pushed the same day) defines exactly seven encodings: gpt2, r50k_base, p50k_base, p50k_edit, cl100k_base, o200k_base, o200k_harmony (https://raw.githubusercontent.com/openai/tiktoken/main/tiktoken_ext/openai_public.py). o200k_base: 199,998 mergeable ranks (contiguous 0–199,997, all 256 single bytes present), specials `<|endoftext|>`=199999 and `<|endofprompt|>`=200018, n_vocab 200,019. o200k_harmony (gpt-oss) reuses the identical ranks and regex and adds 1,091 special strings mapping to 1,090 distinct ids (`<|endofprompt|>` and `<|reserved_200018|>` both = 200018), n_vocab 201,088; named specials `<|startoftext|>` 199998, `<|return|>` 200002, `<|constrain|>` 200003, `<|channel|>` 200005, `<|start|>` 200006, `<|end|>` 200007, `<|message|>` 200008, `<|call|>` 200012. cl100k_base: 100,256 ranks + 5 specials (n_vocab 100,277). Plain text encodes identically under o200k_base and o200k_harmony.

**Model mapping.** `tiktoken/model.py` maps the dash-less prefix `gpt-5` (changed from `gpt-5-` in commit 212b893b "Fail open for GPT-5 model tokenisers", 2026-08-17), `o1-`, `o3-`, `o4-mini-`, `gpt-4.5-`, `gpt-4.1-`, `chatgpt-4o-`, `gpt-4o-`, `ft:gpt-4o` → o200k_base; `gpt-oss-` → o200k_harmony; `gpt-4-`, `gpt-3.5-turbo-`, `gpt-35-turbo-`, `ft:gpt-4`, `ft:gpt-3.5-turbo`, `ft:davinci-002`, `ft:babbage-002`, text-embedding-3-* → cl100k_base. `encoding_for_model('gpt-6-astra')` raises KeyError (also `gpt-6-sol`, `gpt-6.1-sol`). The prefix over-matches (`gpt-55` → o200k_base), so tiktoken is a policy statement, not per-model confirmation (https://raw.githubusercontent.com/openai/tiktoken/main/tiktoken/model.py). In the browser libraries only `gpt-tokenizer` resolves current names (gpt-5.1 … gpt-5.6-sol/terra/luna/cyber, gpt-oss-*); js-tiktoken and tiktoken WASM throw for gpt-5.1/5.5/gpt-oss — the visualizer should own its model→encoding table.

**GPT-6 is unconfirmed.** Issue openai/tiktoken#608 "Update for gpt-6 models" (opened 2026-09-24) was closed "not planned" on 2026-10-17 with no maintainer answer (https://github.com/openai/tiktoken/issues/608). PR #616 (opened 2026-10-09, non-member author) maps the `gpt-6` prefix to o200k_base but is unreviewed; its author writes the mapping "still needs confirmation from the OpenAI tokenizer maintainers before merge" (https://github.com/openai/tiktoken/pull/616). The third-party `token-count-compare` experiment counted identical input tokens (44,794) across GPT-5.5, GPT-5.6 Sol/Terra/Luna and GPT-6 Astra/Sol/Luna on 31 fixtures, but its own README says "Equal counts do not establish tokenizer identity" (https://github.com/williamliu-ai/token-count-compare). OpenAI's `gpt-6-astra` model page says nothing about tokenization. Tiktokenizer.com lists GPT-6 as "Local estimate". Label GPT-6 as "o200k_base (assumed, unconfirmed)".

**Pre-tokenizer regexes (verbatim, from openai_public.py).**

```text
o200k_base / o200k_harmony (also Llama 4 and Muse, byte-identical, 274 chars):
[^\r\n\p{L}\p{N}]?[\p{Lu}\p{Lt}\p{Lm}\p{Lo}\p{M}]*[\p{Ll}\p{Lm}\p{Lo}\p{M}]+(?i:'s|'t|'re|'ve|'m|'ll|'d)?|[^\r\n\p{L}\p{N}]?[\p{Lu}\p{Lt}\p{Lm}\p{Lo}\p{M}]+[\p{Ll}\p{Lm}\p{Lo}\p{M}]*(?i:'s|'t|'re|'ve|'m|'ll|'d)?|\p{N}{1,3}| ?[^\s\p{L}\p{N}]+[\r\n/]*|\s*[\r\n]+|\s+(?!\S)|\s+

cl100k_base (current upstream since tiktoken 0.8.0, 2024-10-03 — possessive quantifiers, INVALID in JavaScript):
'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}++|\p{N}{1,3}+| ?[^\s\p{L}\p{N}]++[\r\n]*+|\s++$|\s*[\r\n]|\s+(?!\S)|\s

cl100k_base (pre-0.8.0 equivalent shipped by tiktoken npm / js-tiktoken; byte-identical to Llama 3's pattern):
(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}{1,3}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+
```

JavaScript consequences (verified in Node 26): the o200k pattern compiles verbatim with the `u` flag in engines that support inline modifiers (Chrome/Edge 125, Firefox 132, Safari 26, Node 23) but fails with the `v` flag (unescaped `/` in `[\r\n/]`); the current cl100k/r50k patterns throw "Nothing to repeat" under both flags. JS `\s` ≠ Rust/Unicode `White_Space` on exactly two code points (U+0085 NEL is White_Space but not JS `\s`; U+FEFF is JS `\s` but not White_Space) — a verbatim port diverges from tiktoken on e.g. `' using \uFEFFnamespace'` (own `[220,44173]` vs tiktoken `[71280,4797]`); substituting `\p{White_Space}`/`\P{White_Space}` made an independent implementation identical on 129,885 o200k reference tokens. js-tiktoken 1.0.21 has this bug (22/500 fuzz mismatches); gpt-tokenizer ≥4.0.2 and @huggingface/tokenizers handle it. Unicode-version drift also matters: Python's `regex` module reports Unicode 16, Node 26 Unicode 17, browsers vary; gpt-tokenizer pins Unicode-16 property ranges to stay faithful.

**Vocabulary hosting.** `https://openaipublic.blob.core.windows.net/encodings/o200k_base.tiktoken` is 3,613,922 B (199,998 lines of `base64 rank`, SHA-256 `446a9538cb6c348e3516120d7c08b09f57c36495e2acfffe59a5bf8b0cfb1a2d`, Last-Modified 2024-05-13); cl100k_base.tiktoken 1,681,126 B (SHA-256 `223921b7…`). The host sends **no CORS headers** and answers OPTIONS with 403 "CORS not enabled", so a browser cannot fetch them; `cdn.jsdelivr.net/npm/gpt-tokenizer@4.1.0/data/o200k_base.tiktoken` (byte-identical, ACAO `*`) and `tiktoken.pages.dev` are CORS-enabled fallbacks, but self-hosting is the plan. The compressed floor for o200k data is ~800 KB brotli in every representation (raw .tiktoken 3,529/1,650/1,229 KB raw/gzip/brotli; custom `[len][bytes]` binary 1,560/1,025/809 KB).

**Partial-character tokens are the norm for CJK.** Scanning single code points: o200k_base splits 88.0% of CJK Unified Ideographs (18,477/20,992), 100% of Ext-A and Bopomofo, 93.9% of Hangul, 98.1% of U+1F300–1F6FF emoji; cl100k_base splits 97.4% of CJK Unified. Taiwan-relevant characters split by o200k: 雲 澎 閩 鳳 酥 ㄅㄆㄇㄈ 🇹🇼; by cl100k additionally 臺 灣 雄 嘉 義 屏 東 彰 林 苗 栗 隆 湖 門 馬 祖 繁 體 國 語. In every scanned range, "multi-token character" ⇔ "contains a partial-UTF-8 token". o200k has 1,562 tokens that are not valid UTF-8 (plus 9 valid tokens starting with a BOM); cl100k has 773.

**Reference ids** (identical from Python tiktoken 0.14.0, gpt-tokenizer 4.1.0, js-tiktoken 1.0.21, tiktoken 1.0.22 WASM): see §5.3.

### 3.2 Anthropic

**Nothing public for Claude 3+.** Official docs describe only `POST /v1/messages/count_tokens` and never link a tokenizer (https://platform.claude.com/docs/en/build-with-claude/token-counting). Anthropic maintainers said in March 2024 that "it's no longer possible to provide ahead-of-time client-side accurate token counts" (https://github.com/anthropics/anthropic-sdk-python/issues/375); the legacy repo `anthropics/anthropic-tokenizer-typescript` was archived on 2026-09-01 and its README says "As of the Claude 3 models, this algorithm is no longer accurate" (https://github.com/anthropics/anthropic-tokenizer-typescript). Anthropic's own skills doc warns tiktoken "undercounts Claude tokens by ~15-20% on typical text, and by much more on code or non-English input" (https://raw.githubusercontent.com/anthropics/skills/main/skills/claude-api/shared/token-counting.md). Do not present tiktoken as a Claude proxy.

**Three tokenizer generations.** (1) Claude 1/2 era, public: 64,995 BPE ranks (ids 5–64999) + 5 specials (`<EOT>`=0 … `<SOS>`=4) = 65,000, GPT-2-style byte-level BPE, pat_str `'s|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+` (no `(?i:)`, compiles in JS), shipped as `claude.json` (696,615 B; 315,810 B gzip) in `@anthropic-ai/tokenizer` 0.0.4 (2023-07-05; npm metadata Apache-2.0, LICENSE file MIT) and mirrored as `Xenova/claude-tokenizer` (byte-identical vocabulary, adapted from the Python SDK's tokenizer.json that was removed in SDK 0.39.0 — an official-but-obsolete artifact, not a reconstruction). (2) Claude 3 → Opus 4.6: unpublished. (3) Opus 4.7 (2026-04-16) and later — Opus 4.8, Opus 5, Opus 5.5, Sonnet 5, Sonnet 5.5, Haiku 5.5, Fable 5/5.1, Mythos 5/5.1, Mythos Preview — unpublished; docs: "approximately 30 percent more tokens for the same text"; Anthropic's Opus 4.7 announcement and the Opus 5.5 migration guide say "roughly 1.0–1.35×" (https://platform.claude.com/docs/en/models/opus-5-5/migration-guide). Independent measurements: Simon Willison 1.46× on an English system prompt (https://simonwillison.net/2026/Apr/20/claude-token-counts/); fenic's `count_tokens` ratios vs cl100k show English 1.05→1.36 but Traditional Chinese 0.79→0.79, Simplified 0.92→0.92, Japanese 0.83→0.84 — **the ~30% inflation is Latin-script-specific; CJK counts are essentially unchanged across generations** (https://github.com/typedef-ai/fenic/pull/407).

**count_tokens API.** Response is only `{"input_tokens": N}` (no boundaries). Free; separate RPM limits 5,000 / 10,000 / 20,000 for Start / Build / Scale tiers; documented as an "estimate" that "might include tokens added automatically by Anthropic" (ctok measures a fixed per-message frame of 7 tokens on v3, 11 on Opus 4.7, 6 on Opus 4.8+, +2 on Opus 5.5). Current docs make `Authorization: Bearer <key>` primary and `x-api-key` a "legacy fallback"; `anthropic-version` is required (current `2026-10-21`; `2023-06-01` still works); keys not scoped to a workspace must send `anthropic-workspace-id` or receive a 400. Verified by both verifiers with curl: the endpoint is CORS-enabled when the request carries `anthropic-dangerous-direct-browser-access: true` (OPTIONS → 200 with `access-control-allow-origin: *`, requested headers echoed; a POST without the header carries no CORS headers). **Correction to the labs researcher**: a browser can call it directly with a user's key; no Worker proxy is needed. Exceptions: ZDR organizations get no CORS ("route requests through a backend proxy server", https://platform.claude.com/docs/en/manage-claude/api-and-data-retention), Covered Models (Fable/Mythos) return 400 for ZDR orgs, and `tool_choice` any/tool is rejected on 5.5-generation models. Simon Willison's `claude-token-counter.html` is a working precedent of exactly this static-page pattern (https://github.com/simonw/tools/blob/main/claude-token-counter.html).

**Model lifecycle for ground truth.** All Claude 3.x models are retired; Opus 4 / Sonnet 4 retired 2026-06-15; Opus 4.1 retired 2026-08-05; `claude-sonnet-4-5-20250929` deprecated, retires 2026-11-30. Still-callable pre-4.7 (old-tokenizer) models: `claude-opus-4-5-20251101` (retire not sooner than 2026-11-24), `claude-haiku-4-5-20251001` (floor already passed), `claude-opus-4-6` (≥2027-02-05), `claude-sonnet-4-6` (≥2027-02-17). Use Opus 4.6 / Sonnet 4.6 as durable v3 references (https://platform.claude.com/docs/en/about-claude/model-deprecations).

**ctok** (`sanderland/ctok`, PyPI 1.3.0, MIT, Python ≥3.12, single dependency `regex`): reconstructs count behaviour for three families — v3 (48,792 pieces incl. 467 byte-fallback atoms; Claude 3–Opus 4.6; 962,053/962,054 exact on the Goldfish corpus), v4.7 (15,283 pieces; 962,054/962,054), v4.8 (= v4.7 vocabulary with a six-token frame; Opus 4.8, Sonnet 5, Fable 5). Opus 5's "trailing ASCII whitespace free" rule is intentionally not modelled; Opus 5.5's +2 tokens not yet modelled. Author's analysis: minimum-piece tiling (MinGram/PathPiece-like), NFC + control stripping, curly-quote folding on v3 only, UTF-8 byte fallback "only within a character and strictly prefix-based", Han/Korean/emoji character-by-character, digits in groups of 3; "none of it is from official sources" (https://github.com/sanderland/ctok, https://tokencontributions.substack.com/p/on-the-biology-of-claudes-tokenizer). `tokenize()` returns "one valid minimum-cost tiling, not a claim about Anthropic's exact segmentation". No JS port exists (a Java port, `clemensrunge/ctok-java`, does; npm `@ctok/*` and `ctok-cli` are unrelated heuristic estimators). Data: `pieces_v4_7.json` 1,086,653 B, `pieces_v3.json` 3,639,018 B (both include per-piece witnesses that can be stripped). **Legacy vocabulary caveats.** `countTokens()` in the archived package applies `text.normalize('NFKC')` before encoding ('ｆｕｌｌｗｉｄｔｈ ＡＢＣ' → 3 tokens vs 36 raw; 'ﾀﾞ' → 'ダ'), so to keep byte alignment the visualizer must encode the raw string with the Tiktoken instance (or js-tiktoken/lite) and never through `countTokens()`; ctok indicates the real Claude 3+ tokenizer does **not** NFKC-fold (fullwidth ｱ becomes byte pieces). Other community "Claude" tokenizers: `ai-tokenizer` (raw counts ×1.1 + overheads; 97.6–99.9% count agreement; no Opus 4.7+ entries), `bpe-lite` (remaps ids, breaks emoji round-trip — unusable for spans), `@lenml/tokenizer-claude` (legacy 65k port), `javirandor/anthropic-tokenizer` (streaming trick since patched by Anthropic).

### 4.2 Verdict: build the tiktoken-format core, buy the SentencePiece engine, keep oracles in CI

1. **Build engine A** (byte-level BPE, tiktoken semantics): regex pre-tokenize → UTF-8 encode each chunk → if the whole chunk is in the vocab emit it (ignore_merges) → otherwise repeatedly merge the adjacent pair with the lowest rank, recording each merge → spans = cumulative token byte lengths. Two independent implementations (~45 lines each) reproduced tiktoken WASM and @huggingface/tokenizers ids over 65k–130k reference tokens per vocabulary (3 test strings + zh-TW/ja/en Wikipedia + 20k-char adversarial text) for o200k, cl100k, Llama 3, Llama 4/Muse and Grok-2, **only after** `\s`/`\S` were rewritten to `\p{White_Space}`/`\P{White_Space}` and `(?i:'s|'t|'re|'ve|'m|'ll|'d)` was expanded to `(?:'(?:[sSſ]|[tT]|[rR][eE]|[vV][eE]|[mM]|[lL][lL]|[dD]))` (U+017F ſ is the only non-ASCII code point that `(?i:s)` matches under `u`; verified by enumeration). It covers OpenAI, Meta, xAI (Grok-2) and the legacy Claude vocabulary with one code path and is the only way to get merge steps for a step-by-step animation (none of the libraries exposes them). Add a priority-queue merge for long inputs. gpt-tokenizer's `BytePairEncodingCore` (MIT, 15 KB gz, 83 MB/s) is the fallback if the team prefers not to own the merge loop, but its internals moved three times in October 2026.
2. **Buy engine B** for Gemma: `@huggingface/tokenizers` 0.2.0 fed with a minified Gemma 4 `tokenizer.json` (or vocab + merges regenerated client-side from the 4.47 MiB `.spiece.model` — the HF `generate_merges` port reproduced all 514,906 merges in identical order in 0.95 s). SentencePiece BPE is whole-text character-level BPE (one "word" after `Replace(' '→'▁')`), needs a priority-queue merge, byte fallback with fuse_unk, and matching of 6,410 USER_DEFINED symbols; writing it is "moderately harder" and is a Phase-2 item if step-by-step merges for Gemma are wanted. Google's `_processor.ts` is a licence-compatible reference.
3. **Oracles**: Python tiktoken 0.14.0 + sentencepiece 0.2.x + HF tokenizers in CI; tiktoken WASM, @sctg/sentencepiece-js and llama3-tokenizer-js in Node tests. Golden fixtures: the ids in §5.3 plus U+0085/U+FEFF/U+2028/U+3000, BOM-prefixed tokens, ZWJ emoji, combining marks, digit runs, CRLF, Unicode-17 code points.
4. **Pitfalls to encode as tests**: `TextDecoder` strips a leading BOM by default and silently corrupts the 9 o200k ranks starting `EF BB BF` (use `{ignoreBOM:true}` or byte keys); all tiktoken-family libraries **throw** when input contains a special-token string (use `encode_ordinary` / `allowedSpecial:'all'` / `disallowedSpecial: new Set()`); js-tiktoken needs the `!`-marker compressed rank format while tiktoken WASM accepts both (a `_` marker panics the WASM); single-byte tokens are never id == byte (o200k byte 0x9D → id 251; Grok-2 id = 128 + byte; Gemma id = 238 + byte).

## 5. Byte-alignment feasibility

### 5.1 Data model

Per token store `{id, bytes: Uint8Array, byteStart, byteEnd, partial, special, zeroWidth}` with offsets into the UTF-8 encoding of the tokenizer's (possibly normalized) text; keep `normalizedDiffersFromInput` and a normalized-text row for the one tokenizer that normalizes (legacy Claude NFKC, if that mode is kept). Tokens may be zero-width (Grok-1's `▁` prefix, BOS) and may start or end mid-character or span the end of one character and the start of the next (Grok-2 token 4242; legacy Claude token 20094 = `E3 83 BC E3 82`). Never derive bytes from `decode([id])` strings — a byte fragment decodes to U+FFFD and the bytes are unrecoverable (a fatal `TextDecoder` throws on a lone `0xE5`).

### 5.2 Algorithm per family

**tiktoken byte-level BPE (o200k, cl100k, Llama 3, Llama 4/Muse, Grok-2, legacy Claude).** `bytes(id)` = base64-decoded rank entry (or, for HF `tokenizer.json`/`.tokens` strings, each char mapped through the inverse GPT-2 `bytes_to_unicode` table — one char = one byte; e.g. `'åı°'` → `E5 8F B0`). Spans are cumulative. The invariant `concat(bytes) == utf8(input)` is guaranteed, not merely observed: there is no normalizer, no unk path, and every vocabulary contains all 256 single-byte tokens (verified for o200k, cl100k, Llama 3, Llama 4, Grok-2, Claude legacy). Grok-2's native `tokenizer.tok.json` already lists bytes per token.

**SentencePiece BPE with byte fallback (Gemma 1–4, Grok-1).** Walk tokens in order: if the id is in the BYTE range (238–493 for Gemma 3/3n/4, 217–472 for Gemma 1/2, 69–324 for Grok-1) it covers exactly one byte whose value is `id − firstByteId` (take the value from the id, not from the `<0xNN>` string — in the Gemma 1/2 HF JSON byte id 226 is keyed as a literal `\t`); otherwise it covers `utf8len(piece)` bytes with each `▁` standing for the space it replaced. Verified contiguous and complete on all test strings (12/12, 36/36, 24/24, … bytes); google-genai's `compute_tokens` returns the same per-byte bytes. Three edge cases, all found by verifiers: (a) a literal U+2581 `▁` in the input (3 bytes) is indistinguishable from a replaced space (1 byte) in piece strings — walk the original input bytes while consuming pieces and let each `▁` match either `0x20` or `E2 96 81` at the cursor, and assert the total; (b) Grok-1's `add_dummy_prefix` makes the first token's leading `▁` a **zero-byte** token — strip exactly one leading `0x20`, unconditionally (a conditional strip breaks on `' leading space'`, whose first token is `▁▁`); (c) SentencePiece's own `SentencePieceText` offsets give zero width to the leading fallback bytes and the whole character to the last one (`('<0xF0>',0,0), ('<0xB0>',0,0), ('<0xBB>',0,0), ('<0x9D>',0,4)`), so the piece-based method above is the only per-byte source and the UI should prefer it (the brief asks for per-byte alignment). Tab is a USER_DEFINED piece (`\t`, id 255968) in Gemma 3/4 but the BYTE piece 226 in Gemma 1/2.

**Semantics policy (owner decision §8.5).** tiktoken-style `encode_ordinary` treats `<|endoftext|>` as text; HF-format engines match special/added strings and emit the id (and `@huggingface/tokenizers` differs from SentencePiece on `<bos>`/`<eos>`/`<pad>`/`<unk>` literals). Default to plain-text semantics everywhere, pass `add_special_tokens:false`, and render BOS as an optional toggle.

### 5.4 Merge-step reproduction

tiktoken's `_byte_pair_merge` (start with one part per byte; repeatedly merge the adjacent pair whose concatenation has the lowest rank; stop when no pair is in the vocabulary) was reimplemented in ~15–30 lines in Python and JS and reproduced the libraries' ids on every chunk, exposing each step: cl100k 灣 → one merge `E7`+`81` → 66285, `A3` left as 96; o200k 日本語 → 7 merges in rank order 985 (`E6`+`9C`), 1024 (`E6`+`97`), 2292, 4087, 9048 (日+本), 9697 (`E8`+`AA`), 40909 (`E8 AA`+`9E`); o200k `' 🇹🇼'` → 5 merges ending with `20 F0 9F`+`87` → 173468. gpt-tokenizer's `encodeGenerator` yields one id array per pre-tokenizer chunk, which gives chunk boundaries for a "pre-tokenization" stage.

### 6.4 Serving behaviour measured on a live Workers static-assets site

- **Edge compression is automatic** and content-type keyed: `Accept-Encoding: br, gzip, zstd` → zstd; `br` → br; `gzip` → gzip; `identity`/`deflate` → uncompressed. Free plan default is Zstandard. Compressible types include `application/json`, `application/javascript`, `text/*`, `application/wasm` and **`application/x-protobuf`**; `application/octet-stream` and `application/gzip` are not compressed. wrangler sets Content-Type from the file extension at upload and **omits it for unknown extensions**, so vocab files must use recognised extensions (`.json`, `.js`, `.txt`, `.wasm`) or get an explicit type via `_headers` (https://developers.cloudflare.com/speed/optimization/content/compression/).
- **Compressed responses have no `Content-Length`** (chunked), so download-progress UIs need a manifest of uncompressed sizes.
- **HTTP Range is ignored**: `Range: bytes=0-99` returns 200 with the full body, no `Accept-Ranges`, and drops `Cache-Control`; the asset worker has no Range code. Lazy loading must use separate files (https://developers.cloudflare.com/cache/reference/range-requests/).
- Default headers: `Cache-Control: public, max-age=0, must-revalidate`, strong ETag (weak `W/` when edge-encoded; `If-None-Match` → 304), `CF-Cache-Status: HIT`, HTTP/3. HTML documents at `/` on three template sites carried **no ETag** (always re-downloaded) — keep `index.html` small. Query strings are ignored for asset lookup; use content-hashed filenames.
- `_headers` can add **and remove** (`! Header-Name`) headers per glob (≤100 rules) but cannot pick a different file; precompressed `.br`/`.gz` siblings are unsupported (workers-sdk issue #3087 closed 2023 without a feature). Verifier disagreement: the hands-on verifier found that `_headers` `Content-Encoding: br` on an uncompressed asset is handled by the runtime re-encoding the body in `wrangler dev` (not double-encoding); the primary-source verifier notes it is undocumented and untested in production. Both recommend not relying on it.
- `.assetsignore` (gitignore syntax) excludes files; `_headers`, `_redirects`, `.assetsignore` are never served; **dotfiles such as `.env` are uploaded and served** unless listed.
- `auto-trailing-slash` 307-redirects `/index.html` → `/`; `404-page` serves the nearest `404.html` with status 404.
- Windows dev gotcha: `wrangler dev` fails with `spawn workerd.exe ENOENT` when the pnpm store path exceeds 260 chars; use a short project path or `MINIFLARE_WORKERD_PATH`; pnpm 12 requires approving `workerd`/`esbuild` build scripts; run `pnpm exec wrangler`, not `npx`.

### 6.5 Compression and caching plan

1. One directory per tokenizer under `/tok/<id>/`, content-hashed filenames, each file < 25 MiB uncompressed, loaded lazily when the tokenizer is selected; a small JSON manifest lists paths, byte sizes, SHA-256 and licence notices for progress UI and integrity checks.
2. Byte-level family: ship `!`-marker compressed tiktoken rank files (`! <offset> <b64> <b64> …`, loads in both js-tiktoken and tiktoken WASM and in the own core) as `.txt`/`.json` so the edge compresses them: o200k ≈ 1.2 MB br, Llama 4/Muse ≈ 1.26 MB, Grok-2 ≈ 0.55 MB, Llama 3 ≈ 0.78 MB, cl100k ≈ 0.6 MB, claude.json 0.32 MB gz.
3. Gemma: ship the 4.47 MiB `gemma3_cleaned_262144_v2.spiece.model` with `Content-Type: application/x-protobuf` via `_headers` (edge-compressed to ~1.65 MiB br) and rebuild vocab + merges client-side in a Worker thread (~1 s desktop; verified identical to the HF JSON), **or** the re-serialized 13 MiB Gemma 4 JSON (3.1 MiB br). Alternatively pre-gzip and decode with `DecompressionStream('gzip')` (baseline everywhere; `brotli` is Firefox 147/Safari 18.4 only) served as an opaque `.bin` so the edge leaves it alone.
4. `_headers`: `/tok/*` and `/assets/*` → `Cache-Control: public, max-age=31536000, immutable`; leave HTML on the default. Keep rules under 100.
5. Construct tokenizers in a Web Worker (JSON.parse + construct 0.3–0.6 s on desktop for 262k-vocab JSON; heap 99–156 MiB per loaded tokenizer in Node — release references when switching, especially on phones). Consider the Cache API for repeat visits.
6. Build-time guard: fail CI if any `dist` file exceeds 25 MiB or `dist` exceeds 20,000 files; run `wrangler deploy --dry-run`.
7. First real deploy: curl the largest asset with `-H 'Accept-Encoding: zstd, br, gzip'` and record `Content-Encoding` and transferred bytes (large-JSON compression on a Free account was extrapolated from a ~199 KB asset, not observed).

Frameworks with first-class assets-only guides: Astro (static, no adapter), Vite + React (`@cloudflare/vite-plugin` optional), SvelteKit `adapter-static` ("compatible with Cloudflare Workers Static Assets"); Cloudflare's Next.js path is vinext (beta)/OpenNext and documents static export only for Pages — avoid Next.js here (https://developers.cloudflare.com/workers/frameworks/framework-guides/astro/, https://svelte.dev/docs/kit/adapter-static).

### 7.2 Layout and alignment

- **Column-first byte grid**: one column per UTF-8 byte (monospaced), three rows — characters (`grid-column: span 1–4`), bytes (hex above dec, or a toggle), tokens (`span N`). Wrap deterministically into rows of K byte-columns computed from the container width (≈8–16 on 360 px phones, 32 on tablets, 48–64 on laptops/4K), splitting a token or a multi-byte character across rows into labelled fragments (continuation marker, shared color), as text highlights break across lines. Interlinear-glossing practice (Leipzig.js, EXMARaLDA) confirms column-first wrapping stacks; tables do not reflow and nested `<ruby>` is out (`ruby-position: alternate` is Firefox-only).
- **Character unit**: code points (each maps to 1–4 bytes) with an optional grapheme bracket drawn with `Intl.Segmenter` (Baseline Widely available since 2026-10-16; Chrome 87 / Safari 14.1 / Firefox 125) so ZWJ emoji and combining sequences read as one glyph.
- **Partial-character tokens** are a primary state: draw the token as a bracket under a subset of a character's byte columns with a hatched/dashed edge where the boundary cuts inside the glyph; show the fragment's hex/dec and a "needs n more bytes" note in the inspector. Offer "merge to grapheme" (tiktokenizer) and "glyph with equal slices" (propathee) only as alternative views.
- **Zero-width tokens** (BOS, Grok-1 `▁`) and a normalized-text row (legacy Claude NFKC) must be representable.
- **Inspector popover**: CSS anchor positioning (Chrome 125 / Firefox 147 / Safari 26, Baseline newly available) with a fallback.

### 7.3 Animation

- CSS `transform` does not apply to non-replaced inline boxes, so FLIP cannot move a wrapping inline token span; animate **atomic cells** (byte/char cells and token segments as grid items) with transform/opacity via WAAPI — Svelte `animate:flip` (sqrt(d)×120 ms, cubicOut, off-main-thread), Motion `layout`/`motion/mini animate()` (3.2 kB), or a 30-line vanilla FLIP. View Transitions can snapshot wrapping inlines (the spec excludes only css-break fragmentation), but each participant needs a unique `view-transition-name` and the page freezes during the update callback, so use them for coarse tokenizer/mode switches, not per-token (Baseline newly available since 2025-10-14: Chrome 111 / Safari 18 / Firefox 144) (https://developer.mozilla.org/en-US/docs/Web/CSS/transform, https://drafts.csswg.org/css-view-transitions-1/).
- Step-by-step merge animation: render the pre-tokenizer chunk, then replay recorded merges (from engine A) one per step with a "just merged" highlight (Cornell demo pattern), scrubbable with ←/→ and a slider; batch steps for long inputs.
- `prefers-reduced-motion: reduce` means replace movement with ≤150 ms opacity/color changes, not remove feedback; detect with `matchMedia` and listen for changes; `MotionConfig reducedMotion="user"` if Motion is used.
- `box-decoration-break: clone` (ship `-webkit-` too) for wrapped inline backgrounds; CSS Custom Highlight API (Chrome 105 / Firefox 140 / Safari 17.2) to color a textarea mirror without DOM wrappers — no semantics for assistive tech, so it complements, not replaces, focusable cells.

### 7.4 Interaction, accessibility, performance

- WAI-ARIA APG **layout grid**: one tab stop per visualization, arrow keys move across cells, Up/Down switch tier keeping byte position, Home/End, Enter/Space pins the inspector, Esc unpins; roving tabindex with `aria-label` (index, id, bytes, char); the same inspector opens on tap (toggle) and pointer hover; synchronize highlight across tiers and the textarea selection (hex-editor pattern). WCAG 1.4.1: never hue alone — add 1 px borders/brackets and alternating lightness ≥3:1; ≥4.5:1 text contrast inside tokens; visible keyboard-help line.
- CJK IME: treat `InputEvent.isComposing` input as provisional, finalize on `compositionend`, never treat Enter during composition as a command (check keyCode 229 as fallback).
- Long input: tokenize in a Web Worker with request ids (drop stale results), yield with `scheduler.yield()` (Chrome 129 / Firefox 142; `setTimeout` fallback), pre-layout rows and virtualize with TanStack Virtual or `content-visibility: auto` + `contain-intrinsic-size`; existing tools cap at 500 tokens/page or hide output above 10k chars. Measured encode cost is sub-millisecond for the default example and 3–20 ms for 10k CJK characters, so the main thread is fine for keystroke-level updates; vocab parse/construct (0.2–0.6 s desktop) belongs in the Worker.
- Theming/responsive: color tokens on `:root` for light/dark; `clamp()` cell sizes from 360 px to 4K; `pointer: coarse` to enlarge hit targets.
- Examples: keep 台灣台南 default; add chips 鯖, 龜, 𰻝, 👩‍👩‍👧, 🇹🇼, 熱鬧, 臺灣, 東京タワー, "Hello 台灣!", `2024年10月`, "I'm here\n\n code();", and a long CJK paragraph; show a per-tokenizer badge (exact / inferred / legacy / reconstruction).

## 8. Decisions that need the project owner's input

1. **How to represent Anthropic.** Options: (a) legacy Claude 1/2 vocabulary (65k, byte-exact spans, obsolete) labelled "Claude 1/2-era public vocabulary — not the Claude 3+ or Opus 4.7+ tokenizer"; (b) JS port of ctok v4.7/v4.8 (MIT; count-exact on published corpora; "one valid tiling, boundaries not guaranteed"); (c) count-only via BYOK `count_tokens`; (d) omit Anthropic with an explanatory panel. **Recommended default**: (a) + (c) now, (b) as Phase 2 after owner sign-off; show the generation-aware frame (7/11/6) and the fact that CJK counts barely change between generations.
2. **Accept the xAI Community License for Grok-2?** It requires shipping the Agreement, the exact notice, a prominent "Powered by xAI", AUP compliance and is revocable; commercial use only within the AUP. Options: Grok-2 with attribution; Grok-1 only (Apache-2.0, 2024 vocabulary, pedagogically rich byte fallback); both. **Recommended default**: Grok-2 primary with attribution panel (site is non-commercial), Grok-1 as a "historical" secondary.
3. **Secondary tokenizers per lab.** cl100k_base (splits the default example; MIT), Llama 3.x (needs "Built with Llama" + Agreement + Notice; EU AUP clause does not apply to text-only 3.0/3.1), Gemma 1/2 256k (Gemini 1.x; Gemma Terms pass-through), Grok-1 (Apache-2.0). **Recommended default**: include cl100k and Grok-1; include Llama 3 only if the attribution burden is acceptable; skip Gemma 256k.
4. **BYOK live-verification panels** (Anthropic `count_tokens` totals; xAI `tokenize-text` with real token bytes; both CORS-open, key kept in memory only). Options: include opt-in; omit. **Recommended default**: include, opt-in, with an explicit warning, model pickers limited to active models, workspace-id field, and ZDR-org failure messaging.
5. **Special-token text policy.** Plain-text semantics everywhere (`encode_ordinary`, `add_special_tokens:false`) vs. matching special strings as the libraries do (and HF vs SentencePiece differ on `<bos>`). **Recommended default**: plain text, with an "allow special tokens" toggle and a visible badge when a special id appears.
6. **Character-tier unit.** Code points (1–4 bytes each; natural for the byte tier) vs grapheme clusters (user-perceived). **Recommended default**: code points with a grapheme bracket; keyboard navigation moves by code point in the char tier.
7. **Vocabulary asset format for Gemma.** `.spiece.model` + client-side merge regeneration (~1 s, smallest: 1.65 MiB br) vs re-serialized 13 MiB JSON (3.1 MiB br, simplest) vs pre-gzipped blob + `DecompressionStream`. **Recommended default**: start with the minified Gemma 4 JSON for correctness, switch to the protobuf path if mobile load time demands it.
8. **Engine ownership.** Own byte-level BPE core (merge steps, full control, ~100 lines + priority queue) vs gpt-tokenizer `BytePairEncodingCore` (fast, but private-API churn). **Recommended default**: own core, with gpt-tokenizer and tiktoken WASM as test oracles.
9. **Framework.** Svelte 5 (built-in `animate:flip`, small runtime, adapter-static on Workers) vs Vite + React + Motion (`layout` FLIP, larger ecosystem) vs Astro with islands. **Recommended default**: Svelte 5 via Vite (plain assets-only deploy); React + Motion if the implementation team prefers it. Avoid Next.js on Cloudflare for this project.
10. **Browser support floor.** Safari < 26 / iOS 18 lack inline regex modifiers and old Safari lacks WASM SIMD. **Recommended default**: support Safari/iOS 16.4+ by never relying on native `(?i:)` (use the expanded alternation) and avoiding WASM in the critical path.
11. **Labelling of inferred mappings.** Show GPT-6, Gemini 4 Argon, Muse Wonder and Grok 4.7 as "inferred" rows under their lab's proxy tokenizer, or list only confirmed models. **Recommended default**: list them with an "inferred — unconfirmed by the lab" badge and a dated source note, backed by a data file with per-entry confidence and URLs.
12. **Deployment identity.** workers.dev subdomain only vs a custom domain (requires a Cloudflare-managed zone; unlocks Compression/Cache/Transform Rules). **Recommended default**: workers.dev first; add the domain when one exists.

## 9. Open questions and risks

- **Mapping drift.** GPT-6 → o200k_base, Gemini 3.6/3.8/4 Argon → Gemma 262k, Muse Wonder → Llama 4/Muse 202k, Grok 4.7 → Grok-2 131k are all inferred. Watch openai/tiktoken releases and PR #616, `python-genai/_local_tokenizer_loader.py` for a gemini-4 entry, Meta Model API docs, and xai-org on HF (a Grok 3 / "0.5T" open release would add a new tokenizer file). Re-verify before launch and periodically.
- **Anthropic fidelity.** No boundary ground truth exists for Claude 3+; the legacy vocabulary and ctok tilings can mislead an educational audience. ctok does not yet model Opus 5 / 5.5 offsets; its vocabulary estimates and "not BPE" claim are unofficial. Real `count_tokens` totals for the test strings were not measured (no key in the research environment).
- **Licence obligations.** xAI licence is revocable and requires notices; Llama 4 AUP withholds the grant from EU-based distributors for multimodal models (avoid by sourcing from Muse Glimmer); Gemma Terms let Google restrict usage remotely (avoid by sourcing from Gemma 4); OpenAI rank files have no explicit licence statement (relying on MIT redistribution by gpt-tokenizer/tiktoken npm). `@anthropic-ai/tokenizer` metadata is inconsistent (MIT vs Apache-2.0).
- **Regex semantics.** `\s` vs `White_Space`, `(?i:)` support, possessive quantifiers in upstream cl100k/r50k, Unicode-version drift in `\p{L}`/`\p{N}` between engines (Node 26 = Unicode 17; tiktoken's Rust tables ≈ Unicode 16). Pre-tokenization of newly assigned code points can differ by browser.
- **SentencePiece edge cases.** Literal U+2581 in input, Grok-1 zero-width prefix, Gemma 1/2 `\t` byte key, `<bos>` literal semantics, Gemma 3 vs 4 BOS defaults.
- **Mobile performance and memory** are unmeasured: 262k-vocab JSON costs 0.3–0.6 s and 99–156 MiB heap in Node; the protobuf rebuild path costs ~1 s desktop CPU. Budget a Worker, lazy loading, and one tokenizer resident at a time.
- **Cloudflare behaviours.** 25 MiB per-file cap (Gemma/Muse/Llama 4/gpt-oss JSON exceed it), no Range, no Content-Length on compressed responses, HTML without ETag, dotfiles served, file-count limit enforced only at deploy, large-JSON compression on a Free account not yet observed.
- **Default example** does not exhibit the partial-character case on o200k, Llama 4/Muse or Gemma — the headline feature needs the extra example chips.
- **Library churn.** gpt-tokenizer rewrote its BPE core in 4.0.1–4.1.0 (Oct 15–18 2026) and its private byte APIs moved; js-tiktoken/tiktoken WASM have had no release since 2025-08-09 and lack o200k_harmony; @huggingface/tokenizers may add character offsets (PR #30) but not byte offsets.
- **Data currency.** Epoch's CSV was updated 2026-10-24 but contains no model dated after 2026-10-15; LMArena placements beyond #1 are unverified; Muse Spark closed-model launch dates come from press.
- **Verification gaps.** `@agnai/web-tokenizers` parity was never exercised (ESM import has no exports); Gemma `Hello, world!` and `日本語のテキスト` were not run with exactly those strings; Muse Spark Open tokenizer identity rests on size parity and HF's statement (repo gated).
